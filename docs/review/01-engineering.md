# 01 — Engineering review (senior software engineer)

Reviewer persona: senior software engineer (TypeScript/React, Java/Spring, Python, production data pipelines).
Commit reviewed: `main` at `3868013`, local Docker stack, 2026-11-23. Scratch scripts and outputs are in
`docs/review/_scratch/eng/` and screenshots in `docs/review/_screenshots/eng/`. Every repro below can be re-run from
those scripts. Finding IDs are `ENG-xxx`.

## 1. Verdict

boqlet is better engineered than most AI-built codebases of this size, especially on the backend.
- **Strong:** the HTTP contract is generated, unknown fields are rejected, and access control is centralised. I swept 55
  calls across orgs and every one answered `404`. Runs are immutable blobs with a rebuildable row index, and the security
  basics are in place (Argon2id, an exact Origin check, signed content length, guards against zip bombs, formula injection
  and CSV injection).
- **Weak:** the engine's business logic, the code that produces the numbers. I found and reproduced:
  - a string-decoding bug in the only expression evaluator, which breaks every non-ASCII name in rules and maps;
  - an over-count when a rule is broken down by material;
  - FLOOR with a step that gives wrong results;
  - a rule configuration that makes a run fail to save its result, every time;
  - two rules that count the same element twice without any warning;
  - user-written regexes that let any project viewer hang the shared engine.
- **Product gaps:** the browser cannot upload a model above 100 MiB. The sheet's payload grows with the element count,
  because every line carries its element trace.
- **Tests:** many, often good, but they test the paths the authors thought of. None of the defects above is covered.

My overall verdict: a sound architecture with an engine that needs a correctness hardening pass, plus property-based and
adversarial tests, before more firms rely on its numbers.

**ENG-001 (repro, `engine/.venv`, PYTHONUTF8=1)**
```
>>> Expr().evaluate('"béton"', {})                         -> 'bÃ©ton'
>>> Expr().evaluate('CONTAINS(name, "béton")', {'name': 'Béton armé'})  -> False
>>> Expr().evaluate('name = "Ziegel ä"', {'name': 'Ziegel ä'})          -> False
```

Through the product (`_scratch/eng/dupq.mjs nonascii`): a rule whose selector is `"béton" = "béton"` matches, because
both sides are mangled the same way. Comparing against *model data* (`material = "Béton"`) never matches. The
system presets avoid non-ASCII in expressions today (I scanned `presets/**`), which is why the Duplex and preset
tests pass. Any firm writing its own rules in its own language hits this immediately.

In the material breakdown, each material should get gross area × its thickness, and the parts should sum to the
