## 1. Verdict

On clean, prismatic elements the engine is accurate: 22 independent checks on 7 samples (walls with
and without openings, slabs, footings, columns, beams, roofs, ceilings, windows) agree with my hand
arithmetic and with my own mesh arithmetic to better than 0.1 %, and every line traces back to GlobalIds,
formula, settings and shares. Accuracy fails where the model is wrong or unusual. The engine trusts the
model's own quantity sets over its geometry even when they disagree by a factor of 1,000 (S09: a
146 m² ground floor billed as **146,199 m²**, 13 m³ of concrete as **13,243 m³**). In those cases it only
asks non-blocking questions that recommend keeping the file's value. Its default rules also understate
or misstate some common items: walls whose body is not a full prism (−9 % on the Duplex party wall,
−11 to −16 % on S07 walls), formwork to non-straight footings (−75 %), pile caps (+205 % area, +280 %
formwork), and external walls coded as internal on every model except the Duplex. Federation also
resolves conflicting duplicate elements without asking. **I would not sign off a BoQ produced this way
as issued.** I would accept it as a well-traced first take-off, to be signed off only after a QS has
answered every contradiction, checked every line over a plausibility limit against the viewer, and
re-coded the walls. With fixes to QS-001…QS-007 it would be close to a sign-off for Revit-quality
models.

## 5. Assumptions and judgement calls

- **A1.** "As modelled" + global-seed + ACME cost codes (the CLI default, also the baseline `default`) is the configuration judged. The Duplex sample in the browser uses the same rule set. A fresh org has no classification by default (context §8), so the Excel "Unclassified" observation (QS-016) applies to that case.
- **A2.** The face area of a wall (length × height less openings, one face, no reveals) is the reference for a wall measured in m². Most methods I have used (NRM2 principle, VOB-style practice, regional practice) measure walls on a face or centreline, not by volume ÷ nominal thickness. I state the principle only and quote no standard text. For uniform prisms the two agree, as the OK rows show.
- **A3.** For steel the reference is the member's physical length (cut length / body length) × nominal kg/m. The difference against Revit's analytical length is a judgement (QS-012, low).
- **A4.** "Script" uses the same geometry kernel (IfcOpenShell) as the engine. To guard against a shared kernel error, every hand-checkable row was also done by hand from raw STEP values, and hand and script agree everywhere. Surface-model and Brep elements (party wall, ceiling, SketchUp walls, roof parts, S04 ring footing) are script-only.
- **A5.** The script's `side_mean` takes faces whose normal is within ~18° of the thin horizontal axis. That is right for straight walls. Curved walls were not part of the check set.
- **A6.** The wall-faces-vs-area survey (§3.3) parses the engine's own measure log (`faces a … / b …`). I cross-checked it against my script on the party wall (49.201 both).
- **A7.** QS-010 was reproduced in-process: `get_boq` on the Duplex with decisions `contradiction:{thickness,volume}:IfcWall:Party Wall - CMU Residential Unit Dimising Wall = geometry` → `stats.decisionsApplied 0`, party wall line 76.6, notes unchanged (`_scratch/qs/revision.py` and an inline run; output in this session's log).
- **A8.** QS-018 was reproduced by parsing `fixtures/ifc/Ifc2x3_Duplex_Architecture_v2.ifc` and running as-modelled: `warnings []`, no check on `1FM6kRbt1Q98O7nMvcxWi0`. v2 is a synthetic fixture (a renamed door, a window without an opening), so its realism is limited.
- **A9.** Severity reflects the risk of a wrong number reaching a client. QS-001 is critical even though the root cause is a defective export, because the engine detected the conflict and still kept the wrong value as the recommended answer.
- **A10.** I did not upload S07/S08/S09 through the browser (shared single-job worker). Their app-level evidence is the stack baseline (`baseline/stack/S09-default` shows the same 146,199.06 m²) and the in-process engine, which the worker runs unchanged.
- **A11.** The sample project's pre-answered decisions (QS-017) were read through the API with my own session (`_scratch/qs/pw-api.mjs`). No data was changed: no answers, no edits, no runs started in the shared org.
- **A12.** The eight KNOWN rows in `verify-quantities` encode today's (wrong) app values with notes, as asked, so the tool runs clean against the current code. When a fix lands, the row turns FIXED (exit 0; `--strict` fails), and the expectation should then be updated.
