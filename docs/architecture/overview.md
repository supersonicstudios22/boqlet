# Architecture overview

How boqlet is built: the components, the stack, the repository layout and the key flows.
Checked against the code on 2026-11-21. Each component has its own page (links at the end).

## Components

```text
 Browser ── Next.js app (apps/app) ────────── same origin: /api/v1 → Java API (rewrite in dev, Traefik on the pilot)
   │  UI only; typed client from openapi.yaml; SSE for live updates
   │
   │  PUT / GET signed URLs (uploads, downloads)
   ▼
 Object storage (S3 API; SeaweedFS)  ◄────────┐
   IFC, parsed.json, geometry.glb,            │
   meshes.npz, results, exports               │
                                              │
 Java API (services/api) ─── SQL ──► PostgreSQL 16 (all queryable state, the jobs table, realtime_events)
   users, orgs, projects, models, BoQs,       │
   runs, Library, decisions, exports,         │  jobs: HTTP dispatch, or Postgres queue (queue_claim / renew / finish)
   shares, notifications, billing, admin      │  rpc:  HTTP (check, names, code lists, templates)
   SMTP outbox ──► mail                       ▼
                                   Engine worker (engine/ifc_boq, Python)
                                     parse, run, preview, diff, export_xlsx, import_boq_edits
```

| Component | Owns | Never |
|---|---|---|
| **Next.js app** | Screens, interaction, client state, optimistic UI, i18n rendering, 3D display (three.js) | Computes quantities or evaluates formulas (BR-01); talks to the engine; holds secrets |
| **Java API** | Identity and sessions, tenancy and permissions, every entity in the data model, state machines, entitlements and usage, audit, notifications and email, job orchestration, ingesting engine results into rows, extension points for modules | Measures, applies rules, evaluates formulas, parses IFC, reads or writes spreadsheets |
| **Engine worker** | Everything that reads IFC, applies rules, or reads or writes spreadsheets | Knows about users, orgs, permissions or plans |
| **Object storage** | Large immutable blobs | Anything that needs querying |
| **PostgreSQL** | Queryable state, the job table, realtime events | IFC or big JSON blobs (it stores keys) |

**Code boundary.** Anything that decides something belongs in the engine, as plain functions over the
contract types (data in, data out, no HTTP, no storage); the backend stores, permits and schedules.
Engine module boundaries: [engine.md](engine.md).

## Stack

| Layer | Technology (versions pinned in the manifests) |
|---|---|
| App | Next.js 16 (App Router, `output: "standalone"`), React 19, TypeScript; Tailwind 4 with shadcn/ui (style base-mira, Base UI); TanStack Query, Table and Virtual; next-intl; three.js (viewer); `@microsoft/fetch-event-source` (SSE); Vitest; Playwright (`e2e-java` only) — `apps/app/package.json` |
| HTTP contract | OpenAPI 3 (`packages/api/openapi.yaml`, 162 operations), TS client with openapi-fetch; Java interfaces and DTOs generated by openapi-generator at build time |
| Backend | Java 21, Spring Boot 3.5 (web, validation, JDBC with `JdbcTemplate`, security, actuator, mail), Flyway, AWS SDK v2 (S3), BouncyCastle Argon2id, Micrometer + OpenTelemetry; virtual threads — `services/api/pom.xml` |
| Engine | Python 3.10–3.13: ifcopenshell 0.8, numpy, trimesh, manifold3d, networkx, openpyxl, jsonschema; FastAPI + uvicorn (HTTP worker), psycopg 3 (queue worker), boto3 — `engine/requirements.txt` |
| Engine contract | TypeScript types in `packages/types/src` → JSON Schemas (`npm run codegen`), validated by the engine ([contracts.md](contracts.md)) |
| Data | PostgreSQL 16; S3-compatible object storage (SeaweedFS 4.53 locally, on the pilot and in tests) |
| Realtime | Server-sent events only: `GET /api/v1/events`; DB triggers write `realtime_events` and `pg_notify`; replay by `Last-Event-ID` |
| Auth | Native email + password (P50): Argon2id, opaque `boqlet_session` cookie (HttpOnly, SameSite=Lax), exact-Origin check on state-changing requests, one active session. Keycloak OIDC kept only as a rollback |
| Deployment | Docker images; Docker Compose with Traefik on one Contabo host (the pilot); GitHub Actions rollout from `main` ([../operations/](../operations/pilot.md)) |

## Request types

1. **CRUD** (most calls): app → API → PostgreSQL, synchronous.
2. **Quick engine calls (rpc)**: preset check, names in a model, code-list read and build, preset
   templates. The API calls the worker's `POST /rpc/{op}` over HTTP with a 15 s timeout, because
   editing can't wait for a queue.
3. **Jobs**: parse, run, preview, diff, export_xlsx, import_boq_edits. The API creates a `jobs` row; a
   worker executes it; the API ingests the output into rows and notifies; the app follows progress over SSE.
4. **Uploads and downloads**: signed URLs straight to object storage (multipart above 100 MiB).

## Key flows

**Upload and parse.** `ModelController.createModelVersion` → `Models.createVersion` (status
`awaiting_upload`, signed PUT) → the browser PUTs the file → `completeModelUpload` → `Models.complete`
(dedupe by SHA-256, BR-08, or enqueue `parse`) → HTTP: `JobDispatcher` → `WorkerClient` →
`POST /jobs/parse`; queue: `worker_queue` claims, runs `worker.execute`, `queue_finish` notifies
`job_finished` → `Jobs.ingest…` → `ParseJob.finished` → `Models.ready` → SSE `job.finished`.

**BoQ run.** `RunController` → `Runs.generate` (inputs from `BoqInputs`: model versions, resolved
preset JSON, decisions, line overrides) → `run` job → `worker._run` → `pipeline.get_boq` → result
(`result.json.gz`) and workbook to storage → `RunJob.finished` → `RunIndex` bulk-loads `run_lines`,
element links, questions, warnings and log entries (`PostgresCopy`). A run with blocking questions
ends in `needs_input` (a run state, not a job state, P13).

**Export.** `ExportController` / `BoqExports` → `export_xlsx` job → `exports` row →
`GET /exports/{id}/download` gives a signed URL. A saved version's export is its frozen file (BR-25).
Public share Excel is rendered synchronously through the worker.

**Sign-in.** A setup link (`native_setup_links`, from `issue-setup-link.sh` or `npm run local:user`)
or an invitation → `POST /auth/set-password` → `POST /auth/sign-in` (Argon2id, rate limits, a session
row) → `boqlet_session` cookie → `NativeIdentityFilter` checks the session on every request and the
Origin on writes. A second session gets `409`; the client retries with `takeover` and the first is
signed out (`session.revoked` over SSE).

**Live updates.** Entity and job triggers → `realtime_events` + `pg_notify('boqlet_events')` →
`EventWakeup` → `Realtime` SSE stream (heartbeat 25 s, 5 min per stream, replay by `Last-Event-ID`) →
app `src/realtime/sse.ts` → TanStack Query invalidations. Works across several API instances.

## Design choices and why

| Choice | Why |
|---|---|
| Engine as a worker with a JSON job contract | Heavy work never blocks the API; Java needs no Python (D61, D67) |
| PostgreSQL job table first, two transports (HTTP dispatch, Postgres queue) | One less moving part; enough for pilot volumes; a broker can replace it behind the same contract |
| Results ingested into rows | Paging, filtering, grouping, viewer index and comparisons without loading big JSON (D65) |
| SSE, not WebSocket | One-way server → browser is all that's needed; works through proxies |
| OpenAPI for HTTP, JSON Schemas from `packages/types` for engine shapes | One source of truth across three languages (D64) |
| Engine owns all spreadsheet I/O | One implementation (openpyxl) |
| Formulas evaluate only in the engine | One evaluator (`expr.py`); editors preview through engine jobs, never in the browser or Java |
| The pricing module is separate and removable | The core never depends on it ([modules.md](modules.md), P36) |
